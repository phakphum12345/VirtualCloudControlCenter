# 1. Long-term First

## Principle

ทุกการตัดสินใจของโปรเจกต์ต้องให้ความสำคัญกับความยั่งยืนในระยะยาวมากกว่าความสะดวกหรือความรวดเร็วในระยะสั้น

## Rules

- ออกแบบให้รองรับการขยายระบบในอนาคต
- ลด Technical Debt ให้เหลือน้อยที่สุด
- หลีกเลี่ยงการเขียนโค้ดซ้ำ
- ใช้ Single Source of Truth
- แยกหน้าที่ของแต่ละโมดูลอย่างชัดเจน
- ทุกการเปลี่ยนแปลงต้องสามารถดูแลต่อได้
- ทุกการเปลี่ยนแปลงต้องไม่ทำลาย Architecture หลัก
- เอกสาร โค้ด Tests และ Build ต้องสอดคล้องกันเสมอ

## Decision Order

เมื่อมีหลายทางเลือก ให้พิจารณาตามลำดับดังนี้

1. ความถูกต้อง (Correctness)
2. ความปลอดภัย (Security)
3. ความสามารถในการดูแลรักษา (Maintainability)
4. ความสามารถในการขยายระบบ (Scalability)
5. ประสิทธิภาพ (Performance)
6. ประสบการณ์ผู้ใช้ (User Experience)
7. ความรวดเร็วในการพัฒนา (Development Speed)

หากเกิดความขัดแย้ง ให้ลำดับที่อยู่สูงกว่ามีความสำคัญก่อนเสมอ

## Required Before Commit

- Architecture ยังถูกต้อง
- ไม่มีการสร้างหนี้ทางเทคนิคโดยไม่จำเป็น
- ไม่มีโค้ดซ้ำโดยไม่มีเหตุผล
- ไม่มี Dependency ที่ไม่จำเป็น
- เอกสารอัปเดตตามโค้ด
- Tests ผ่าน
- Build ที่เกี่ยวข้องผ่าน
- มีหลักฐานการเปลี่ยนแปลง เช่น Tests, CI, ADR หรือผลตรวจสอบ

## Forbidden

- แก้ปัญหาแบบชั่วคราวโดยไม่มีแผนแก้ถาวร
- เพิ่ม Framework หรือ Dependency โดยไม่มีเหตุผล
- เพิ่ม Backend เพื่อแก้ปัญหาที่ Flutter จัดการได้
- เพิ่มความซับซ้อนโดยไม่จำเป็น
- ลดคุณภาพเพื่อให้เสร็จเร็ว
- เขียนเอกสารที่ไม่ตรงกับโค้ดจริง
- Commit งานที่ยังไม่ผ่าน Quality Gate โดยไม่ระบุข้อจำกัดอย่างชัดเจน

## AI Rule

AI ทุกตัวที่ทำงานกับโปรเจกต์นี้ต้อง

- เลือกแนวทางที่ดีที่สุดในระยะยาว
- อธิบายเหตุผลเมื่อการเปลี่ยนแปลงมีผลต่อ Architecture
- รักษาโครงสร้างหลักของระบบ
- ไม่เพิ่มหนี้ทางเทคนิคโดยไม่จำเป็น
- ไม่ละเมิด Constitution ของโปรเจกต์
- ไม่อ้างว่างานเสร็จจนกว่าจะมีหลักฐานจากการรันจริง

## Project Policy

สำหรับโปรเจกต์ Phaqui:

- Flutter เป็นแกนหลักของระบบ
- ไม่มี Laravel
- ไม่มี Backend Server
- ไม่มี Google Calendar API
- Google Drive ใช้เฉพาะ Backup, Restore และ Sync ตามสิทธิ์ของผู้ใช้
- ทุก Platform ใช้ Source Code ชุดเดียวเท่าที่ข้อจำกัดของระบบอนุญาต
- ทุก Platform ใช้ Icon ต้นฉบับชุดเดียว
- Windows ต้องมีไฟล์ `.ico`
- ทุก Build ต้องผ่าน GitHub Actions ก่อนเผยแพร่

## Definition of Done

งานจะถือว่าเสร็จเมื่อ

1. โค้ดครบตามขอบเขต
2. เอกสารตรงกับโค้ดจริง
3. Format ผ่าน
4. Analyze ผ่าน
5. Tests ผ่าน
6. Build ที่เกี่ยวข้องผ่าน
7. Commit อยู่บนสาขางาน
8. ยังไม่ Merge จนกว่าผู้ใช้จะสั่ง

## Goal

สร้างระบบที่สามารถพัฒนา ดูแล และขยายต่อได้อีกหลายปี โดยไม่ต้องรื้อ Architecture ใหม่
