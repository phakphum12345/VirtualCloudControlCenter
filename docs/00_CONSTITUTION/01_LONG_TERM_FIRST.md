# 1. Long-term First (Enterprise Rule)

## Mission

ทุกการตัดสินใจของ AI และนักพัฒนาต้องเลือกแนวทางที่ดีที่สุดสำหรับอนาคตของโปรเจกต์ แม้ว่าจะใช้เวลามากกว่าในวันนี้

## Priority

การตัดสินใจทุกครั้งต้องเรียงตามลำดับนี้

1. Correctness
2. Security
3. Architecture
4. Maintainability
5. Scalability
6. Testability
7. Performance
8. User Experience
9. Development Speed

ห้ามสลับลำดับโดยไม่มีเหตุผลที่บันทึกไว้

## AI Mandatory Workflow

AI ต้องทำตามลำดับนี้ทุกครั้ง

1. วิเคราะห์ปัญหา
2. วิเคราะห์ผลกระทบ
3. ตรวจสอบ Architecture
4. ตรวจสอบ Constitution
5. วางแผนการแก้ไข
6. แก้ไขโค้ด
7. รันการตรวจสอบ
8. แก้ไข Error ทั้งหมด
9. รันใหม่จนผ่าน
10. Commit
11. รายงานผล

ห้ามข้ามขั้นตอน

## Required Before Commit

ก่อน Commit ทุกครั้ง ต้องผ่านทั้งหมด

- `dart format --output=none --set-exit-if-changed .`
- `flutter analyze`
- `flutter test`
- GitHub Workflow ผ่าน หาก Workflow นั้นเกี่ยวข้องกับการเปลี่ยนแปลง
- เอกสารอัปเดตและตรงกับโค้ดจริง
- Architecture ยังถูกต้อง
- ไม่มี Duplicate Logic โดยไม่มีเหตุผล
- ไม่มี Dead Code ที่ทราบอยู่แล้ว
- ไม่มี Temporary Code ที่ไม่มีแผนถอดออก
- ไม่มี TODO ที่ไม่มีเจ้าของ ขอบเขต หรือแผนดำเนินการ

หากข้อใดไม่ผ่าน ห้ามอ้างว่างานเสร็จ และห้าม Merge

การ Commit ระหว่างแก้ไขทำได้เฉพาะเมื่อระบุอย่างชัดเจนว่าเป็นงานระหว่างดำเนินการและมีหลักฐานสถานะจริง

## Forbidden

ห้าม

- แก้ปัญหาเฉพาะหน้าโดยไม่มีแผนแก้ถาวร
- เพิ่ม Technical Debt โดยไม่บันทึกเหตุผลและแผนชำระ
- ลดคุณภาพเพื่อให้เสร็จเร็ว
- เขียนโค้ดซ้ำโดยไม่มีเหตุผลทางสถาปัตยกรรม
- เพิ่ม Framework หรือ Dependency โดยไม่จำเป็น
- เพิ่ม Backend เมื่อ Flutter และบริการที่อนุมัติแล้วจัดการได้
- Merge หากยังไม่ผ่าน Quality Gate ที่เกี่ยวข้อง
- เขียนเอกสารที่ไม่ตรงกับโค้ดจริง
- รายงานผลการรันที่ไม่ได้เกิดขึ้นจริง

## Flutter-only Policy

โปรเจกต์นี้ใช้

- Flutter เป็นแกนหลัก
- Local Storage สำหรับข้อมูลหลักในอุปกรณ์
- Google Drive สำหรับ Backup, Restore และ Sync ตามสิทธิ์ผู้ใช้
- GitHub Actions สำหรับ Quality Gate, Build และ Release

ห้ามเพิ่มโดยไม่ได้รับอนุมัติจากเจ้าของโปรเจกต์

- Laravel
- PHP
- Backend Server
- Google Calendar API
- Firebase

## Build Policy

การเปลี่ยนแปลงต้องรักษาความสามารถในการ Build ของแพลตฟอร์มที่ได้รับผลกระทบ

- Android
- iOS
- Windows
- macOS
- Linux
- Web

ข้อกำหนดไอคอน

- ทุกแพลตฟอร์มใช้ต้นฉบับไอคอนชุดเดียว
- Windows ต้องมีไฟล์ `.ico` ที่ถูกต้อง
- Android, iOS, macOS, Linux และ Web ต้องใช้รูปแบบไอคอนที่เหมาะกับแพลตฟอร์ม

แพลตฟอร์มที่ไม่สามารถรันใน Runner ปัจจุบันต้องมี Workflow หรือหลักฐานการตรวจสอบบน Runner ที่รองรับ ห้ามอ้างว่า Build ผ่านโดยไม่มีผลการรัน

## AI Responsibility

AI ต้องไม่รายงานว่า

- “เสร็จแล้ว”
- “ผ่านแล้ว”
- “แก้แล้ว”
- “Build สำเร็จแล้ว”

จนกว่าจะมีหลักฐานว่า

- แก้ไขจริง
- รันจริง
- ตรวจสอบผลจริง
- แก้ Error ที่เกี่ยวข้องจริง
- Commit จริง เมื่อผู้ใช้สั่งให้ Commit

หากยังทำไม่ครบ ต้องรายงานสถานะ ข้อจำกัด และขั้นตอนที่เหลือตามความจริง

## Definition of Done

งานถือว่าเสร็จเมื่อครบทั้งหมด

1. ขอบเขตงานถูกนำไปใช้ครบ
2. โค้ดและเอกสารสอดคล้องกัน
3. Format ผ่าน
4. Analyze ผ่าน
5. Tests ผ่าน
6. Build หรือ Quality Gate ที่เกี่ยวข้องผ่าน
7. ไม่มีข้อผิดพลาดที่ทราบแล้วถูกปกปิด
8. มีหลักฐานจาก CI, Tests, ADR หรือผลตรวจสอบที่เหมาะสม
9. Commit อยู่บนสาขางานตามคำสั่ง
10. ยังไม่ Merge จนกว่าเจ้าของโปรเจกต์จะสั่ง

## Goal

สร้างระบบที่สามารถพัฒนา ดูแล ทดสอบ และขยายต่อได้อีกหลายปี โดยไม่ต้องรื้อ Architecture ใหม่ และรักษาคุณภาพของโค้ด เอกสาร และกระบวนการพัฒนาให้สอดคล้องกันเสมอ
